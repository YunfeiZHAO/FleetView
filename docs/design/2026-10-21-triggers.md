# Triggers: what will make an agent act on its own

| | |
|---|---|
| **Date** | 2026-10-21 |
| **Status** | Built on branch `triggers`; not deployed |
| **Code** | `Status/AgentTriggers.swift`, `State/AppState+Triggers.swift`, `UI/TriggersPanel.swift`, `/triggers` + `/trigger/cancel` |

A card that looks idle can have a cron behind it. `code_sense 生产` (20319a26) was the case that
asked for this: a `CronCreate` job, `9,29,49 * * * *`, firing a 3,500-character fleet-monitor prompt
into the session every twenty minutes, and nothing on the board said so. Now a chip on the card
says how many such things there are; clicking it opens a panel that lists them and deletes them.

## Three kinds, three sources

| Kind | What | Where FleetView learns it |
|---|---|---|
| `cron` | Claude `CronCreate`, and `/loop` wakeups (`ScheduleWakeup`) | the Stop hook's `session_crons` |
| `background` | background shells, monitors, subagents that wake the session when they report | the Stop hook's `background_tasks` |
| `launchd` | a LaunchAgent whose command line names the terminal (`progress-ping.sh <uuid>`) | `~/Library/LaunchAgents/*.plist`, once a minute |

**Session crons exist only in the CLI process.** `CronCreate` says so in its result ("Session-only
(not written to disk, dies when Claude exits)"), and 2.1.280 reports `durable` as unavailable. No
file lists them. The one authority is the CLI, and it reports them at the end of every turn: the
Stop hook payload carries `session_crons: [{id, schedule, recurring, prompt}]` (prompt clipped at
1,000 characters with a `… [+N chars]` marker) and `background_tasks: [{id, type, status,
description, command?}]`. hook.sh already forwarded the whole payload; `EventWatcher` had been
dropping these two keys. Verified against a real Stop from 20319a26 on 2026-10-21.

So the list is "as of the end of the agent's last turn", and the panel says so. The gaps that leaves
are covered without guessing:
- **The process dies** (back to the shell, window closed, session killed, not reconnected after a
  relaunch): a report only counts while the card's status is an agent status.
- **A new process starts** (`SessionStart` startup/resume): the report is dropped.
- **A one-shot fires**, **a wakeup fires**, **background work reports**: each of those is a turn,
  and the turn ends with a fresh Stop.
- **A recurring cron hits its 7-day expiry**: it fires once more first (Claude's rule), which is a
  turn.

Reports are cached in `~/.fleetview/triggers.json` — not state.json, since losing it costs a chip
until the next turn — because agents outlive a FleetView relaunch and a daily cron would otherwise
vanish from its card for a day.

**Codex** has no session scheduler (codex-cli 0.163); a Codex card can only show launchd jobs.

## What the transcript adds

Read only when the panel (or `/triggers`) asks, incrementally like `TokenUsage`, with a substring
pre-filter so a 75 MB transcript costs 0.37 s the first time and nothing after: when each cron was
made, its whole prompt, how many times it fired and when last (fires are user records carrying
`scheduledTaskId`), and which one-shots are `/loop` wakeups (their `ScheduleWakeup` call reports no
id; matched on the prompt).

**Jitter.** 20319a26's job, set for :09 :29 :49, fired at :18:48 :38:48 :58:48 — Claude adds a fixed
per-job delay. "Next 23:29" would be wrong by ten minutes every time, so the last fire's lateness
is carried forward and shown as "next ~23:38".

## Deleting

**launchd**: `launchctl bootout gui/<uid>/<label>`, then the plist goes to the Trash (recoverable).

**Session crons and background work can only be deleted by the agent.** Nothing outside the
process reaches its store — no file, no slash command, no signal. So FleetView types one exact
instruction into the terminal ("Call CronDelete with id "fa91d4ca" now … do nothing else"; TaskStop
for background work; for a wakeup, also "do not call ScheduleWakeup again") and marks the row
"sent, waiting" until a later report no longer lists it, or 15 minutes pass and the delete button
comes back. It costs one short turn, and the instruction shows up as the card's last prompt.

It refuses while the card is "needs you": the text would land in the permission menu as an answer.
A draft sitting in the composer would be sent along with it — the same as any `/type`.

## Removing a card retires its LaunchAgents

`com.fleetview.progress-ping.e4dbb87e` fired every hour for 26 days (≈600 "no live session" lines)
at a card removed on 2026-09-26: the job and the card were tied by nothing but the uuid in its
arguments, and removing a card only archived it and killed its tmux session. Harmless only by luck —
a restore brings a card back under its old uuid, and the pings would have resumed into it. Removed by
hand 2026-10-22 (plist in the Trash).

So `removeTerminal` and `clearBoard` now `retireLaunchdJobs`: every LaunchAgent naming the removed
card (uuid or `fv_` session) is booted out and its plist moved to the Trash, logged and audited
(`fleetview.trigger.launchd_retired`). A job that also names a card still on the board is kept.
Closing a card does not do this — a closed card reopens under the same uuid, and is meant to.

## Not done

- `durable` crons (`.claude/scheduled_tasks.json`): unavailable in the CLI this was built against,
  and none exist on this machine, so their format is unverified. They would be readable and
  deletable from the file directly.
- LaunchAgents left over from cards removed before the retiring above existed are not shown
  anywhere: there is no card to put them on.
- `auto-recover.sh` acts on every terminal and names none, so it is not a trigger of any one card.
